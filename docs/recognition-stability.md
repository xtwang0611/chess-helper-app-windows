# 棋子识别与轮次稳定性优化

开发分支：`codex/recognition-turn-stability`，基于 `windows-port` 的 `209cfae`。
本轮用一个分支处理相互依赖的识别、状态与界面问题；不合并、不推送稳定分支。

## 改动

- 根据可见网格拟合真实格点，不再完全沿用固定像素坐标；允许河界、棋子挡住部分线。
- 棋子中心裁剪使用边界补齐而非平移中心；双尺度推理保留各类别概率。
- 将帅支持九宫内所有合法位置，相/象支持各自七个合法位置；位置规则仅帮助区分有视觉证据的候选，不凭规则补造棋子。
- 按像素内容缓存概率，保留不确定性，1.5 秒后重新推理；刷新、重新定位、重启时清空缓存。
- 连续两次相同、通过数量/位置检查的识别结果才成为已确认局面。连续漏子不再被“强制同步”成新棋局。
- 已确认棋盘在截图异常时保留，清空旧建议并暂停计算；恢复两次有效识别后自动继续。不再凭漏将/漏帅推断胜负或锁进结算状态。
- 初次识别有少量疑点时显示预览，橙色 `?` 是待确认格，不向引擎发送不完整局面。
- 定位检测与遮挡判断分开。检查局部网格证据明显不对称的截图，避免菜单被模型当成空格；提示“信息不足”，不武断断言一定有遮挡。
- 单个顺序识别线程、最多一张待处理截图、定期稳定帧复核；模型异常后线程继续工作。
- 引擎与界面消息都有局面版本，落子/刷新/停止后丢弃旧结果。修正变招重复叠加历史、历史锚点行棋方及真正的引擎读取超时。
- UI 每次批量消费消息，补齐棋盘预览接口，刷新异步执行，停止期间不能再次启动。

## 轮次的使用方式

标准开局可确定红方先行。**首次接入中残局、刷新、重新定位或丢失连续历史后，静态棋盘无法可靠确定谁走。**

先等棋子显示，再点新增的「轮次」，选「现在我方走棋」或「现在对方走棋」。我方默认为屏幕下方的一方。
接下来按识别到的合法落子自动切换；对方回合不会自动支招，「变招」也不会强行计算我方走法。
若对方先落下一步且变化完整，也能自动确定接下来的行棋方，无需额外确认。

## TT / JJ 实机验收（合并前）

两个平台分别完成以下项目，尤其 JJ 尚没有本轮真实棋盘回放样本，不能用 TT 测试代替验收。

1. 正常开局显示全部棋子；连续双方各走五步，界面跟随变化。对手回合不出现新的我方建议或残留箭头。
2. 打开中残局，自动定位、手动框选木质外框分别测试；第一次先确认轮次。
3. 帅在九宫中前进/横移、黑卒过河、双相分别移到中相/边相位置。对照双方棋子数与位置。
4. 打开游戏菜单或用其他窗口遮住一部分棋盘：暂停建议，不误报胜负、不把漏子同步进去；移开后自动恢复。
5. 移动/缩放游戏窗口，或点击刷新、重新定位：旧建议消失，新棋盘重新显示。重新确认轮次后能计算。
6. 计算过程中落子、停止、重新开始、点击变招：过期的思考提示和箭头不得回写，按钮仍可响应。
7. 实战持续十分钟，观察是否出现越来越慢、长时间空棋盘或重复报警。图像稳定但持续待确认时，保留诊断样本。

## 单张图片诊断

```powershell
python scripts/diagnose_recognition.py .\tests\fixtures\tt_endgame_309.png --platform TT
python scripts/diagnose_recognition.py C:\path\board.png --platform JJ --details
```

桌面截图可附 `--crop 左 上 宽 高`。输出为 JSON：格点坐标、棋盘数组、前三候选概率、不确定格、各区域网格证据和耗时。
默认不写图片、不改变配置、不启动截图或引擎。`--export-crop 路径.png` 是可选的显式导出功能。

## 边界

本轮未重新训练 ONNX 模型，不能保证所有皮肤、缩放、动画都零误识别。
规则不能可靠纠正“合法格点上极高置信度的错误类别”；这类情况需要真实失败截图继续补回归/训练数据。
遮挡检测是保守的视觉检查，不是对所有遮挡的保证。信息不足时宁可保留已确认棋盘、暂停建议。
连续漏子不会自动当成新残局；若确实更换到了只少子而没有移动的编辑局面，点击刷新重新建立基线。
